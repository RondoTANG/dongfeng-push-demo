# 项目决策记录

## D-001 本期流程终点

本期完成“线索采集→来源处理→事件聚合→AI 补证研判→事件审核→两类初始作业草案→分别审批”，并补充原创增长的后续分支：“登记实际发布结果→接收后效指标快照→计算同口径增量→运营判断→按需生成原创后二次加热草案→独立审批”。正式作业下发、用户触达和互动执行仍延后，页面不得展示为已完成。

## D-002 本地可运行架构

后端采用 FastAPI＋SQLite，前端采用无构建步骤的 HTML、CSS 和原生 JavaScript。页面核心数据只来自真实 API，状态在刷新和重启后保留。

## D-003 Codex 的介入方式

Codex 心跳自动化每三小时唤醒并调用本地运行器；Codex 通过工作项 API 领取补证／分析任务并结构化回传。服务负责状态、规则、审计和持久化。MCP 仅为未来可能路径，本期不实现也不作为前置依赖。

## D-004 公开搜索的产品定位

豆包 Global Search 和 Codex 公开搜索属于“公开信息线索来源”，不是专业舆情数据源。搜索数据的热点结论固定为 `unknown`，必须展示不可判定原因。

## D-005 确定性与生成式能力分工

URL 归一、去重、无效过滤、状态流转、配置版本、审批和审计由确定性程序执行；AI 负责语义归纳、证据补充、存疑说明和草案文本，不承担字符级 JSON 透传和数据库确定性状态写入。

## D-006 配置与凭证分离

品牌、查询、来源、清洗、聚合和草案规则可配置并在运行中冻结版本；API Key 只从环境变量或 macOS Keychain 读取，不进入业务配置、数据库、页面或版本库。

## D-007 实体主数据颗粒度

首期只维护 9 个品牌及别名。车型、人物、活动在事件中动态识别；新实体或证据不足时输出存疑原因，与事件结论一起交人工审核，不要求维护一份容易过期的全量实体字典。

## D-008 UI 设计基线

沿用成长体系后台的左侧栏、顶栏、灰底白卡、紧凑筛选和数据表设计语言；不复制成长体系业务代码，不采用营销官网、大标题、重复标语或 PPT 式卡片堆叠。

## D-009 双路作业对象必须分开

“原创增长”和“源内容加热”是同一事件下两种并列的初始决策。源内容加热直接作用于热点事件中的目标文章或视频，不等待原创投稿。原创实际发布后另有“原创后二次加热”分支，它绑定发布记录和后效判断。三类草案使用独立 `draft_purpose`、目标字段校验和审批状态。

## D-010 源内容加热必须绑定可执行目标

源内容加热草案必须引用当前事件证据中的 `target_source_id`，并保留目标平台、目标URL、内容标题和互动动作。官网列表页、普通网页、平台不明、无有效链接或无法确认可互动状态的来源不得生成此类草案；系统只校验目标可执行性，是否值得放大仍由运营确认。

## D-011 冻结规划的修订处理

`memory/project-startup-plan.md` 是 S2 冻结基线，不回写历史原文。本次用户确认的双路作业方向以本决策、当前项目记忆、字段地图和真实代码为准，覆盖冻结规划中“仅原创草案”的旧范围描述。

## D-012 原创发布后效是原创增长的后续分支

保留热点源内容直接加热，同时补齐原创发布后的后效追踪。只有已审批原创可登记实际发布结果；至少两个同一内容、同一平台、同口径快照后，确定性程序才计算首末增量。运营选择“生成二次加热草案”时创建 `draft_purpose=original_post_boost`，绑定 `target_submission_id` 与触发判断并独立审批。数据异常不自动生成草案，系统不自动执行点赞、评论等互动。
