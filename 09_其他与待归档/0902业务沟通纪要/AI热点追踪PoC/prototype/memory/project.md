# 项目记忆

## 项目定位

- 项目名称：东风护卫军 AI 热点线索与作业草案联动 PoC
- 当前迭代：AI热点线索PoC：双路作业草案生成与审批。
- 迭代说明：本地可运行原型，以豆包与 Codex 双路公开搜索形成可追溯线索，支持定向补证、原创增长草案、已发布原创的快照观察、运营判断和追加加热草案审批；事件有可执行关联内容时，另行支持直接加热草案。
- 创建日期：2026-09-04
- 产品形态：护卫军 B 端运营后台＋本地 FastAPI 服务＋SQLite 持久化。
- 参考底座：`04_成长与激励体系/04_成长体系UI原型` 的后台布局与视觉规范，仅参考、不修改原项目。

## 产品目标

验证公开搜索线索能否经过统一清洗、事件聚合、证据研判和人工审核，形成原创增长草案；原创实际发布后登记链接、接收同口径指标快照、观察增量，由运营决定是否生成追加加热草案。事件已有可执行关联内容时，另行验证直接加热支路。业务终局希望识别真实热点并自动组织响应；本期不承诺真实热点判定，也不替代专业舆情数据源。

## 当前能力与业务期望的差异

| 业务期望 | 本期可验证 | 本期明确不能证明 |
| --- | --- | --- |
| 发现哪个平台、哪个事件正在快速发酵 | 从豆包公开搜索和 Codex 可访问网页中发现东风相关公开线索，识别来源平台并聚合事件 | 未知链接前的全平台完整覆盖、平台原生互动量和连续增速 |
| 判断是否是真实热点并及时响应 | 给出证据、缺失项、风险提示和“是否值得形成作业草案”的运营建议 | 仅凭搜索结果数量或 AI 主观评分判定真实热点 |
| 判断哪些热点值得发原创作业 | 运营基于公开线索、证据、风险和品牌关系选择“原创增长”，系统生成原创评论／内容草案并单独审批 | 系统自动证明真实热点、正式作业下发和任务执行 |
| 判断如何加热热点源内容 | 运营从事件证据中选择具体平台文章或视频，系统生成绑定目标URL和互动动作的源内容加热草案并单独审批 | 自动证明目标内容真实热、自动集中点赞／评论 |
| 原创发布后是否继续加热 | 登记已审批原创的实际发布链接，接收现有采集、业务推送或人工凭证的指标快照，计算同口径增量并由运营决定是否生成二次加热草案 | 跨平台统一阈值、快照不足时自动判断、自动执行点赞／评论 |

## 目标用户

- 运营审核人员：处理事件候选、核验证据、修改并审批作业草案。
- 产品管理员：维护品牌、查询、来源、清洗、聚合和任务规则。
- 数据／规则管理员：检查运行覆盖、失败原因、配置版本和审计记录。
- 研发或 IS 观察者：评估接口、稳定性、数据边界和后续企业化改造条件。

## 核心页面列表

1. 运行中心：查看手动运行、双路任务覆盖、分步数量、耗时和失败原因；明确自动采集暂停及运行冷却时间。
2. 信息线索工作台：按来源平台、品牌关系、有效状态和时间筛选线索。
3. 事件详情：查看聚合来源、证据时间线、品牌关系、存疑原因并完成人工结论。
4. 作业草案与审批：查看原创增长、热点源内容加热和原创后二次加热三类草案；分别编辑、通过和驳回。
5. 原创后效追踪：登记实际发布链接，查看指标快照和增量，保存运营判断并按需进入二次加热草案。
6. 配置管理：可读化展示并维护品牌、查询、来源、清洗聚合、草案生成、后效快照和热点数据准入规则。
7. 无效与审计记录：分开记录自动无效、人工否决、配置变更和关键操作。

## 核心用户路径

运行批次创建 → 豆包与 Codex 执行同一查询目录 → 统一来源并保留多路发现记录 → 自动无效过滤 → 事件聚合 → 如有明确问题则预览并确认定向补证 → 运营审核事件 → 判断是否生成原创增长草案 → 审批与实际发布。如事件存在可执行关联文章或视频，可另行生成直接加热草案并审批。

原创增长后续分支：已审批原创实际发布 → 登记发布结果 → 接收至少两个同口径快照 → 计算增量 → 运营判断 → 按需生成原创后二次加热草案 → 独立审批与审计留痕。

流程在“草案审批结果已记录”处结束，不向正式护卫军系统推送。

## 主要数据对象

- `collection_run`：一次完整运行批次及覆盖、配置快照和提供方结果。
- `query_job`：运行批次中的单条查询任务及重试状态。
- `raw_provider_result`：提供方原始响应索引，原文不在前端泄露凭证。
- `source_item`：统一后的公开来源内容。
- `source_discovery`：同一来源被哪个搜索工具、哪条查询、在什么时间发现的多路追溯记录。
- `invalid_log`：自动无效结果及规则原因。
- `event`／`event_evidence`：统一事件、聚合来源与证据。
- `candidate_review`：事件候选的运营审核结论。
- `evidence_request`／`evidence_job`：先预览、后确认、再执行的定向补证计划和单次调用记录。
- `task_draft`：带 `draft_purpose` 的三类草案；源内容加热绑定来源，原创后二次加热绑定实际发布记录。
- `original_publication`：已审批原创对应的实际发布URL、平台、内容ID和发布时间。
- `publication_metric_snapshot`：同一原创内容在不同时间点的指标快照及数据来源。
- `publication_evaluation`：快照增量、数据状态、运营结论和关联二次加热草案。
- `audit_log`：配置和业务操作审计。

## 交付方式

- 本机一条命令启动 FastAPI、SQLite 和静态后台。
- 核心页面只读取真实 API；没有凭证、没有数据或接口失败时展示真实状态，不用前端 Mock 冒充成功。
- 首轮导入或执行真实豆包结果，验证从运行到原创增长草案审批，并用实际或测试发布链接验证后效追踪和追加加热接口；如有可执行关联内容，同时验证直接加热支路。
- 本期只保留每三小时自动化的可接入设计，实际调度默认暂停；完整运行需人工确认且受服务端3小时冷却限制。

## 已确认假设

- 当前为本机单用户 PoC，不实现登录、组织和细粒度权限后台。
- 豆包 Global Search 与 Codex 公开搜索都是本地 PoC 的线索发现手段；两者都不是本项目承诺的企业级热点数据源。
- 搜索来源的 `hotspot_status` 固定为 `unknown`，同时记录不可判定原因。
- 9 个品牌及别名为当前品牌主数据；车型、人物、活动在事件内动态识别，存疑时写原因交人工判断。
- 状态流转、去重、无效过滤、配置快照和审批由确定性程序执行；生成式 AI 不负责字符级 JSON 透传或确定性状态写入。
