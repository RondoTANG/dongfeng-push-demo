## 产品形态

- 面向类型：护卫军 B 端运营工具＋本地可运行 PoC 服务。
- 载体形态：桌面端后台网页，由本地 FastAPI 提供 API 和静态页面，SQLite 持久化。
- 主要角色：运营审核人员、产品管理员、数据/规则管理员、研发或 IS 观察者。

## 项目目的

- 实现目的：将“三小时采集→来源处理→事件聚合→AI研判→原创作业草案→人工审批”做成可运行、可观察、可追溯的本地闭环。
- 评审对象：业务、运营、PMO、IS/研发。
- 需验证的业务假设：公开搜索线索经结构化处理后，能否稳定产生可审核的事件和有证据的原创作业草案。
- 不属于本次验证目标：证明公开搜索结果就是真实热点，或替代专业舆情数据源。

## 项目范围

- 本期模块：运行与自动化、信息线索、事件聚合与证据、任务草案审批、规则配置、无效与审计。
- 本期页面：
  1. 运行中心：三小时任务、手动运行、采集器状态、分步数量和失败重试。
  2. 信息线索工作台：线索列表、来源平台/账号、自动无效、待聚合和待审核。
  3. 事件详情：聚合来源、证据时间线、品牌关系、存疑原因、结论审核。
  4. 作业草案与审批：原创选题、目标平台、用户标签、风险提示、人工审批和审批留痕。
  5. 配置管理：品牌与别名、查询目录、来源平台、清洗聚合、任务生成和热点数据准入规则。
  6. 无效与审计记录：自动无效原因、人工否决、配置变更和完整运行链路。
- 本期服务：
  - 运行编排服务：运行批次、查询任务、重试和步骤状态。
  - 数据获取服务：豆包 Global Search 适配器、Codex 补证入站接口、未来标准数据推送入站接口。
  - 来源处理服务：字段标准化、平台/账号判断、URL 归一、内容去重和无效过滤。
  - 事件聚合服务：事件候选、证据绑定、品牌关系、存疑项和人工合并/拆分。
  - AI 研判服务：语义归纳、不确定原因、原创任务草案；不承担热度数学计算和确定性状态流转。
  - 任务联动服务：候选审核、作业草案、草案修订、人工审批和审批留痕。
  - 配置与审计服务：YAML 规则读取、运行时快照、操作日志和凭证隔离。

## 非本期范围

- 不做模块：C 端护卫军页面、生产级舆情数据中心、通用 MCP 平台。
- 不做页面：用户登录、组织权限后台、外部平台账号管理。
- 不做能力：用搜索结果数判热度、正式作业下发、业务系统消费、MCP 对接、投稿回流、效果加热、公众号/视频号效果自动采集、企业级 7×24 SLA。
- 后续配合：当草案生成与审批链路验证通过后，再另行设计标准事件推送、护卫军业务系统消费或受控 MCP 调用，以及投稿与效果链路。

- 视觉基调：企业级中后台，高信息密度、小字号层级、弱阴影、明确状态色，不使用宣传型大标题或装饰性渐变。
- 是否沿用底座设计：沿用视觉 token 和 B 端布局规则，重新建立统一组件，不拷贝页面 HTML。
- 参考页：`B端_作业管理列表.html`、`B端_反馈审核列表页.html`、`B端_成长数据健康度大盘.html`、`B端_等级规则与XP配置页.html`。
- 禁用风格：营销官网、PPT 式卡片堆叠、超大号标题、高饱和大面积色块、重复标语。

## 整体页面结构

- 导航结构：护卫军后台左侧栏新增一级“AI 热点与作业联动”，子菜单为运行中心、线索工作台、作业草案、配置管理；事件详情和日志从业务列表下钻。
- 页面跳转：运行批次→线索工作台→事件详情→作业草案审批；配置和审计横跨全链路。
- 布局责任：顶栏表达面包屑和执行身份，内容区优先展示状态、待处理数和证据，详情采用主信息＋右侧审核抽屉。

## 核心流程

- 用户入口：运营从运行中心观察自动批次，也可手动发起一次运行。
- 三小时自动化：
  1. Codex 心跳自动化每 3 小时唤醒。
  2. 自动化调用本地运行器创建 `run_id`，本地运行器调用豆包采集并将结果批量入站。
  3. 来源处理和事件聚合由确定性程序执行。
  4. Codex 只领取 `needs_evidence`或 `needs_analysis` 工作项，补充公开证据、语义结论和存疑原因，通过指定 API 回传结构化结果。
  5. 服务生成待运营审核的事件和作业草案，页面展示本轮数量与失败原因。
- 流程终点：运营审批作业草案并留存结论；系统不将草案推送到正式护卫军系统。
- 关键状态：运行待启动/执行中/部分成功/成功/失败；来源有效/自动无效/待判定；事件待补证/待审核/已通过/已否决；作业草案待审批/已通过/已驳回。
- 异常状态：凭证缺失、数据提供方失败、返回结构异常、网络不可达、无结果、全部自动无效、AI 分析超时。

## 验收方向

- 本轮完成后应看到：一套可在本机启动的后台与 API，真实数据能按“运行→来源→事件→审核→作业草案审批”追溯。
- 必须可用页面：6 个页面全部可达，列表、筛选、详情、审批、配置和日志操作有真实接口反馈。
- 必须跑通流程：
  - 手动发起一次豆包真实查询，生成运行批次和来源记录。
  - 选择至少一个事件完成审核并生成作业草案。
  - 可执行脚本验证后，创建并验证每 3 小时的 Codex 自动化。
- 可运行性：页面重新加载后状态仍存在；停掉 API 后页面明确报错；未配置凭证时不伪造成功。
- 标注策略：默认不常驻产品标注图钉；全局验证后按 PM 复制标注提示词统一补充。

## 约束和风险

- 技术约束：首期本地单机，使用 FastAPI＋SQLite＋无构建工具前端；核心流转不依赖生成式 AI 输出的字符级透传。
- 自动化约束：Codex 心跳是本地 PoC 调度方式，不包装成企业级调度承诺；后续可以无损替换为 launchd、企业调度器或专业数据源推送。
- 凭证约束：API Key 继续从 macOS Keychain 读取，不入库、不写前端、不写 Git、不在日志回显。
- 资料风险：公开搜索对社交平台覆盖不完整，页面必须展示“不可判定热点”的具体缺失原因。
- 字段风险：车型、人物、活动为事件内动态识别，不作全量前置主数据；新实体或证据不足时记录存疑原因并交人工。
- 人工核对项：事件是否值得产生作业、目标平台和标签、作业草案及其风险提示均须由运营确认。
