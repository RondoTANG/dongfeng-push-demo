# 护卫军项目综合理解

> 本文是供后续 AI/Agent 接手项目时使用的长期上下文，不替代 PRD、代码、原型、会议纪要和线上数据。
> 最后核实时间：2026-07-28。

## 1. 一句话定义

护卫军是面向东风体系内部员工、网评员及相关运营团队的企业宣传作业平台：运营侧创建并精准分发跨平台内容任务，用户侧领取、执行并提交文本或截图凭证，AI 审核中台完成初审、防作弊和证据提取，人工处理异常与申诉，积分承担兑换激励，XP 承担成长分层与权限控制。

它不是单一“截图审核工具”，而是由任务调度、用户与组织、人群分层、跨平台执行、AI 审核、人机复核、积分/XP、消息触达、内容运营和数据分析组成的业务中台。

## 2. 当前最高优先级结论

### 2.1 当前业务方向

根据 2026-07-24 最新业务会议，当前战略从“批量加热、粗放刷量”转向“阵地声量与真实互动”：

1. 减少无传播价值的批量点赞和灌水评论。
2. 围绕官方账号阵地媒体指数、优质评论和爆款内容持续加热。
3. 从全员粗放分发转向按平台偏好、活跃度、能力和组织归属进行精准分发。
4. 严控积分浪费、短时集中互动和可能导致平台封控的行为。
5. AI 审核必须由“能识别部分场景”升级为“场景覆盖、自动纠错、证据可追溯、人机协同”。

### 2.2 当前刚性交付主线

最新会议给出的节点是当前优先级基准，而非早期原型完成度：

| 时间节点 | 交付主线 |
| --- | --- |
| 2026-08-01 | 作业配置全维度自定义，放开平台、任务类型和图片上传数量等配置 |
| 2026-08-15 | AI 审核场景全覆盖、失败自动触达和链接申诉/纠错 |
| 2026-08-31 | 分发均衡、首批分平台标签与审核后台单屏至少 3 图 |
| 2026-09-30 | 党支部级看板穿透与服务器资源隔离 |

### 2.3 范围冲突的处理原则

成长体系已有完整规划、PRD 和高保真原型，但最新会议明确其为“非核心功能，当前暂停”。因此：

- 积分/XP 双轨、四段位、生态巡航智能体等属于有效的长期产品蓝图。
- 未取得新的恢复排期证据前，不得将成长体系扩建视为当前开发主线。
- 当前任务若与成长体系无关，不应借机扩大范围。

## 3. 用户、角色与核心价值

### 3.1 C 端用户

- 护卫军网评员/内部员工：低成本领取任务、明确执行要求、上传凭证、获得积分、查看审核和申诉结果。
- 高活跃或高能力用户：承接复杂、原创、直播或高质量评论任务。
- 外部大 V、经销商等扩展执行者：在业务转型方向中承担更专业或平台特定任务，具体账号体系和权限仍待产品确认。

### 3.2 B 端角色

- 集团/总管运营：全局规则、跨品牌额度、任务与审核治理、数据总览。
- 子品牌运营：创建作业、配置人群和素材、申请消息额度、跟踪执行。
- 审核人员：处理 AI 异常、失败作业、用户反馈与申诉。
- 组织管理者：按所在党委、下属党委、三级党委和党支部查看完成与活跃情况。

### 3.3 核心业务价值

- 把跨平台宣传动作转为可配置、可分发、可核验、可结算的作业。
- 用 AI 全量初审和人工异常复核降低审核成本，但不能让 AI 黑盒直接承担高风险终审。
- 用组织、人群、平台偏好和活跃度提高任务匹配效率与公平性。
- 用数据闭环衡量真实声量、执行质量和组织表现，而不是只追求提交量。

## 4. 端到端核心链路

### 4.1 常规作业闭环

1. 运营配置作业类型、平台、动作、素材、目标人群、时间、数量、积分和审核规则。
2. 分发引擎依据组织、人群包、标签、轮回覆盖、活跃度和任务门槛投放。
3. 用户在 C 端任务大厅领取，跳转外部平台执行点赞、评论、转发、原创或直播互动。
4. 用户提交文本或截图凭证。
5. 规则引擎先做结构化校验，AI 中台做场景识别、身份/内容/动作核验和防作弊。
6. 可信结果自动通过；失败、低置信、高风险和申诉进入人工复核。
7. 审核结果生成证据链，并触发积分结算、消息通知、统计和用户侧结果展示。

### 4.2 异常与申诉闭环

AI 不应只返回“通过/不通过”。至少需要保留场景分类、关键提取值、匹配状态、规则命中、图片索引/文件名、失败原因和必要的置信信息。低置信或争议结果进入人工复核；用户可查看透明驳回原因并发起申诉，人工结论再更新积分/信用和审核记录。

### 4.3 直播任务升级链路

活动直播与日常直播应分开：

- 日常直播可保留原有简单双截图逻辑。
- 活动直播由 B 端输入带时间/环节的活动大纲，LLM 生成“任务作战图”和视觉映射基准。
- C 端领取后查看/保存任务图，在不同直播环节完成评论和截图。
- 推荐交互是“无序批量上传 + AI 自动归集”，以降低用户认知成本；分槽强引导方案只适用于必须严格对号入座的场景。
- 后端执行视文自洽校验，并结合时间、画面、评论、直播间身份及图片去重判断有效性。

## 5. 作业模型与平台范围

### 5.1 一级作业类型

- 转发
- 原创
- 素材分发作业
- 互动
- 其他作业：专属、直播、其他平台

### 5.2 主要平台

项目资料覆盖微信公众号、微信、微信视频号、视频号直播、抖音/抖音直播、快手、小红书、微博、知乎、B 站、头条号等。具体可用平台必须以当前后台配置和采集/审核能力为准，不能仅凭全景介绍中的“12个平台”断言均已生产可用。

### 5.3 互动动作

点赞、喜欢/在看、转发、评论及其复合组合。不同平台 UI、凭证数量和审核字段不同，作业配置必须数据化，不能继续把图片数量和组合逻辑写死在代码中。

## 6. AI 审核中台理解

### 6.1 当前智能体分工

现有资料呈现出路由与多智能体流水线：

1. Router：先识别朋友圈、直播间、点赞/评论等场景，无效截图提前终止。
2. 场景智能体：按朋友圈、直播、评论、点赞等类别提取昵称、文案、互动状态、直播间名称等。
3. 防伪去重智能体：利用系统时间、画面、弹幕、输入法状态和视觉指纹识别重复图或同一时刻截图。
4. 聚合器：按图片索引合并结果，产出标准化 `detailed_results` 与最终判定。
5. 舆情/评论质量智能体：对评论的相关性、正负向、质量和评分做语义判断。

### 6.2 关键输出概念

- `category`：如 `moments`、`live_stream`、`like_action`、`comment`、`like_comment`、`invalid`。
- 身份匹配状态：`MATCHED`、`MISMATCHED`、`NOT_FOUND`。
- 直播间名称匹配、用户评论匹配、指定文案匹配、图片数量和互动状态。
- 防伪指纹：系统时间、他人弹幕/评论拼接、画面类型等。
- 多图结果必须继承 `index`、`imagename`，便于下游定位证据。

### 6.3 Prompt 工程共识

- 先做场景白名单/黑名单拦截，避免在无关图片上强行找目标导致幻觉。
- 把视觉注意力限定在明确 UI 区域。
- 用“目标图标 vs 明确未激活基准图标”的盲测对比判断高亮，不凭语义常识脑补。
- 明确排除正文 Emoji、系统栏、全局大图标、文本符号等劫持项。
- 内部推理与最终 JSON 必须一致；布尔字段和明细数组必须满足约束。
- 输出必须是稳定可解析的结构化 JSON。

### 6.4 当前主要审核风险

- 最新会议反馈部分场景错误率曾高达 70%，说明 Prompt 原型和样本测试不能等同于生产质量。
- 对“未找到”使用品牌/车型语义兜底可能提高召回，但也容易把不相关截图误判为匹配，必须用真实坏例回归验证。
- 视觉模型容易把正文表情、别人的评论、系统图标或相邻控件当成目标动作。
- 多图直播作业需严格区分基准图、重复图、有效驻留图；缺失时间的宽容策略应保留证据并进入风险分层。
- AI 审核结果必须支持自动纠错触达、人工复核和申诉，不能只继续堆 Prompt。

## 7. 分发、人群与组织

### 7.1 分发方向

资料中存在全量覆盖池、守卫队、尖兵队、轮回分发、白名单和人群包等概念。最新方向要求进一步按平台偏好、活跃度、能力和组织进行精准匹配，同时解决任务领取不均与党委考核数据异常。

### 7.2 用户标签

标签需要同时服务：

- 平台偏好与熟练度。
- 活跃/沉默生命周期。
- 作业质量、完成率和信用风险。
- 组织归属。
- 高难任务或白名单资格。

动态标签、人群包和轮回覆盖的关系必须在后续数据模型中明确，避免规则交叉造成重复投放或分发不公。

### 7.3 党委组织树

项目保存了较完整的员工/用户党委树，包含“所在党委 → 下属党委 → 三级党委 → 党支部”等层级，并存在部分名称重复、简称/全称并存的情况。组织数据应使用稳定组织 ID 作为主键，名称只用于展示；统计与权限不能依赖名称字符串直接关联。

当前刚性需求是看板下钻到党支部，并提供人均完成率等更有管理价值的指标。

## 8. 消息触达与公众号授权

### 8.1 消息额度方案

服务号公共模板消息存在日额度压力，项目设计了双通道：

1. 用户领取任务时通过微信一次性订阅累积个人可用额度，发送时优先核销。
2. 公共额度按常规保留池和预约池分配，支持品牌申请、审批、作业锁定、执行核销、剩余额度自动释放和人工取消预约。

T+1 催办需要合并“未领取 + 未完成”通知，减少单用户额度消耗。推送前由业务侧按任务类型、历史完成和总积分等规则排序；额度耗尽时低优先级用户可能被截断，因此排序是业务规则而非纯技术实现。

### 8.2 公众号监控方案

- 采用微信第三方开放平台服务商扫码授权，禁止向子品牌索要 AppID/Secret。
- 长期保存 `authorizer_refresh_token`，短期令牌自动刷新。
- 监听 `MASSSENDJOBFINISH`，Webhook 需在 5 秒内返回 `success`。
- 以 `ArticleUrl` 或 `MsgID` 做幂等和分布式去重。
- 轻量抓取文章公开元数据后创建 `pending_review` 作业。

现有根目录和 `公众号授权/` 下的 Python/JSON 实现属于 Demo 级，生产化仍需数据库、共享缓存、加密存储、队列、监控、重试和安全审计。

## 9. 成长与激励体系（长期蓝图，当前暂停）

### 9.1 双轨模型

- 积分 Points：外部奖励资产，用于商城兑换。
- XP 成长值：内部段位与权限资产，用于升级、保级、降级和任务准入。
- 两者独立结算，所有文案禁用“高薪、薪酬、工资、佣金”等现金化表达。

### 9.2 设计内容

规划包含四阶段位、XP 获取/扣减流水、动态门槛、保级和降级保护、历史用户迁移、C 端成长中心、B 端规则配置、健康度大盘及生态巡航智能体。竞品参考来自滴滴、京东、携程、东风日产 Ni+ 和上汽大众 V 力值。

### 9.3 未决问题

- XP 阈值、折算系数和通胀模型仍需线上近一年积分数据测算。
- PRD 状态仍为草案，技术评审和数值精算未完成。
- 新旧体系迁移方案、上线灰度和恢复排期均需重新确认。

## 10. 信息架构与原型规范

### 10.1 B 端全局菜单

根 `.agents/AGENTS.md` 定义的 B 端菜单为强制基准：

- 作业管理
- 审核管理
- 用户管理
- 内容管理
- 系统设置
- 统计分析
- 全局悬浮生态巡航分析智能体

局部原型也必须展示完整菜单，不得只保留当前模块。

### 10.2 C 端主导航

- 首页/功能导航
- 作业大厅
- 成长中心
- 个人中心

成长中心当前属于暂停主线，但现有导航结构和原型仍是长期设计依据。

### 10.3 Antigravity 原型习惯

- 同一功能的多状态需同屏平铺展示，不只写文字说明。
- 页面右侧保留固定批注区，动态逻辑写清判断条件、状态差异和兜底。
- B 端侧边栏结构统一，当前页高亮必须与文件名对应。
- 原型假数据应贴合东风护卫军业务，避免无意义占位文本。
- 成长体系子项目有独立 `.agents/AGENTS.md` 和一致性检查技能，仅在该子目录内生效。

## 12. 已知风险与待核实事项

### 12.1 业务与交付风险

- 最新会议对需求响应、体验、AI 效果和运营方式均有明确负面反馈，且节点与合同结算相关。
- 积分储备紧张，任何新增激励或大规模任务都需评估成本与平台风控。
- 需求优先级机制缺失曾导致非核心需求挤占资源。

### 12.2 产品风险

- 作业暂停、资料替换、错误任务锁定等临时变更能力尚需方案。
- 审核后台信息密度不足，影响人工复核效率。
- 用户标签、分发池、人群包和组织层级规则存在交叉，需要统一数据模型。
- 外部平台能力依赖授权、供应商和平台政策，文档字段不等于稳定可用接口。

### 12.3 技术风险

- 当前仓库混合文档、原型、Demo、生成脚本、测试样本和局部应用，不是单一可统一构建的应用。
- 任务堆积与发布链路资源未隔离是已知稳定性问题。
- 公众号 Demo 使用 JSON 文件存储，只适用于演示。
- 部分在线地址和供应商能力来自 Obsidian 归档，使用前应重新验证可访问性和最新状态。

### 12.4 待核实

- 8 月至 9 月刚性节点当前实际完成度和责任人。
- 生产系统真实技术栈、服务边界、数据库表和部署拓扑。
- AI 各场景线上准确率、召回率、人工复核率及坏例分布。
- 现网平台清单、任务类型配置和图片数量是否已完成数据化。
- 用户标签与分发规则的现网口径。
- 组织树主数据来源、组织 ID 和同步机制。
- 成长体系何时恢复及是否沿用现有四段位方案。
